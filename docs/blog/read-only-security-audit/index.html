Read-Only Security Audit in Claude Code: Security Auditor Agent + Subagent Read-Only Guard

Run a security audit with a subagent that can read everything and change nothing, using three components from the aitmpl catalog.

6 min read
Claude Code Security Subagents Hooks Workflow

The Problem: Auditors That Can Also Edit

A security audit should observe. But a subagent that can run Bash or Edit can also "helpfully" fix what it finds, install a package, or rewrite a file mid-review. This workflow combines three components so the auditor can read your whole repository and is unable to change it.

The Three Components

  • Security Auditor agent (agents/security/security-auditor): a specialist subagent for vulnerability analysis and compliance gaps. Its frontmatter allowlists only Read, Grep, Glob.
  • Subagents Explore-Only setting (settings/hooks/subagents-explore-only): a SubagentStart hook that injects an instruction into every subagent: investigate, never change, and report the exact changes you would make.
  • Subagent Read-Only Guard hook (hooks/security/subagent-read-only-guard): a PreToolUse hook that actually enforces it. Inside a subagent it denies Edit, Write, MultiEdit, NotebookEdit and any shell command that is not on a short read-only allowlist.

How They Connect

graph LR
    A[You: audit request] --> B[Main Claude]
    B --> C[Security Auditor subagent]
    C -->|SubagentStart| D[Explore-Only instruction]
    C -->|PreToolUse| E[Read-Only Guard]
    E -->|read-only| F[Read, Grep, Glob, git log]
    E -->|write attempt| G[Denied]
    C --> H[Findings report]
    H --> B

    style E fill:#F97316,stroke:#fff,color:#000

The layers are complementary. The agent's tools list limits what it can call, the setting tells it why, and the guard is the enforcement for anything that slips through, such as a shell command. The guard detects a subagent by the agent_id field in the hook input, so your main conversation is never restricted and can apply the fixes the auditor proposes.

Installation

npx claude-code-templates@latest \
  --agent security/security-auditor \
  --hook security/subagent-read-only-guard \
  --setting hooks/subagents-explore-only
your-project/
├── .claude/
│   ├── agents/security-auditor.md
│   ├── hooks/subagent-read-only-guard.py   # guard script
│   └── settings.json                       # both hooks registered here
└── ...

The guard is a Python script, so python3 must be on your PATH. It does not block reading secrets such as .env; pair it with the env-file-protection hook if that matters for your repo.

Step-by-Step Workflow

Step 1: Install the components

Run the command above from your project root, then start Claude Code and run /hooks to confirm the SubagentStart and PreToolUse hooks are registered.

Step 2: Ask for the audit

claude

> Use the security-auditor agent to audit the authentication code in src/auth
  and the dependencies in package.json. Report findings by severity.

Claude can delegate automatically from the agent's description, but naming the agent explicitly, or @-mentioning it, makes the choice certain.

Step 3: Watch the guard work

If the auditor tries something that changes state, such as redirecting output to a file or running npm install, the guard denies the call and the subagent continues with read-only tools:

Allowed:  grep -rn "jwt.sign" src/        git log --oneline -20 -- src/auth
Denied:   echo "fix" > src/auth/login.js   npm install lodash   sed -i 's/a/b/' file

Step 4: Review the report, then apply fixes yourself

The auditor returns findings with the exact file, location and proposed change. Because the restrictions apply only inside subagents, you can now ask the main conversation to apply the fixes you approve:

> Apply the fix for the JWT expiry finding and add a test for it

Practical Use Cases

  • Pre-release review of a branch you do not want touched.
  • Auditing unfamiliar code such as a vendored library or a freshly cloned repo.
  • CI-style checks where an audit must leave the working tree clean.

Limits to Know

  • The explore-only setting is an instruction, not enforcement. The guard is what blocks writes.
  • The guard does not cover MCP tools.
  • It treats anything it cannot classify as a write, so a few harmless commands may be denied. Ask the subagent to use Read, Grep and Glob instead.
